# gqlkit Refactoring / Re-architecture Plan

- **Status**: Maintainer decisions incorporated (2026-07-04) — see §6 Decisions
- **Date**: 2026-07-04
- **Scope**: `packages/cli`, `packages/runtime`, test infrastructure. `packages/docs` and `examples/` are touched only where imports/goldens require it.
- **Method**: Full-file audit of every source module in `packages/cli/src` and `packages/runtime/src` (8 parallel deep-read passes: one per pipeline stage, plus shared/, runtime, orchestration layer, and test suite), with every claim below re-verified against the actual files. All file:line references were checked against the working tree at commit `56410f5`.

---

## 1. Current State Assessment

### 1.1 Summary

The codebase (~28,000 lines in cli+runtime, excluding testdata) is healthier than "prototype debt" usually implies: the golden-file test suite (~225 cases) is strong, diagnostics are consistently modeled, and the `PipelineContext` reducer style in the orchestrator is clean. The debt is concentrated and specific:

1. **The documented pipeline architecture no longer matches reality.** Stage boundaries exist on paper (`structure.md`) but are bypassed at every seam.
2. **There is no owned intermediate representation (IR).** Core types are homed inside one stage and duplicated (sometimes byte-identical) in others, which forces every inline-type feature to be implemented 3–4 times.
3. **Copy-pasted algorithms have diverged**, producing at least two confirmed user-visible bugs and several latent ones.
4. **~600+ lines of confirmed dead code** and one fully built but unreachable feature (schema pruning).

Each is detailed below with evidence.

### 1.2 Architecture-level findings

#### A. Stage facades don't exist; the orchestrator is the de facto implementation of two stages

`structure.md:86` states "Each stage exposes via `index.ts`, internal structure is encapsulated." In reality:

- `type-extractor/extract-types.ts` is a **1-line type re-export**; `resolver-extractor/extract-resolvers.ts` contains **only type declarations** (87 lines, no functions). Neither stage has an entry-point function.
- The real stage composition lives in the orchestrator: `extractTypesCore` (`gen-orchestrator/orchestrator.ts:154-259`), `extractResolversCore` (`orchestrator.ts:416-455`), and `convertDefineApiToFields` (`orchestrator.ts:283-368`) — the last one *constructs `ExtractResolversResult`*, the type that `resolver-extractor/index.ts` exports as its headline product but never produces.
- Consequently `orchestrator.ts:8-54` deep-imports **9+ internal modules** across stages (`type-extractor/collector/result-collector.js`, `converter/graphql-converter.js`, `extractor/type-extractor.js`, `mapper/scalar-base-type-mapper.js`, `resolver-extractor/extractor/define-api-extractor.js`, …), none of which are exported from any `index.ts`.
- `schema-generator/generate-schema.ts:54-352` is a **second orchestrator**: it calls into `auto-type-generator` at 9+ sites (lines 71, 97, 117, 135, 188, 207, 214, 227, 235), interleaved with a second invocation of type-extractor's `convertToGraphQL` (line 124), and manually merges two parallel resolveType pipelines (lines 188–212).

#### B. The pipeline has cycles

The declared order (type-extractor → resolver-extractor → auto-type-generator → schema-generator, `structure.md:29-33`) is violated in three places:

| Cycle | Evidence |
|---|---|
| type-extractor → auto-type-generator | `type-extractor/converter/graphql-converter.ts:1` imports `isTypenameFieldName` from `auto-type-generator/typename-types.js`; `auto-type-generator/auto-type-generator.ts:19` imports `isEligibleField` back from `type-extractor/converter/field-eligibility.js` |
| resolver-extractor → schema-generator | `resolver-extractor/validator/abstract-resolver-validator.ts:9` imports `BaseType` from `schema-generator/integrator/result-integrator.js`; schema-generator calls back into that validator (`result-integrator.ts:15,541-547`) |
| shared → type-extractor | 9 of 23 `shared/` files import `Diagnostic`/`GraphQLFieldType`/`TSTypeReference` from `type-extractor/types/*` (e.g. `shared/diagnostics.ts:1`, `shared/type-converter.ts:1-4`), while `type-extractor/types/graphql.ts:1-5` imports `DirectiveInfo`/`DeprecationInfo` back from `shared/` |

#### C. No owned IR — the same shapes are declared repeatedly

- `FieldInfo` (`type-extractor/types/graphql.ts:22-29`), `AutoGeneratedField` (`auto-type-generator/auto-type-generator.ts:90-97`), and `BaseField` (`schema-generator/integrator/result-integrator.ts:38-45`) are **byte-identical 6-field interfaces**, bridged by `toBaseField()` (`result-integrator.ts:155-164`) — an "adapter" that performs no transformation.
- `SourceLocation` is defined twice (`shared/source-location.ts:3-7`, `type-extractor/types/diagnostics.ts:1-5`) and inlined twice more (`define-api-extractor.ts:70-74,86-90`).
- `TypeExtension` is defined twice with the same name and different field types (`resolver-extractor/extract-resolvers.ts:75-78` vs `result-integrator.ts:83-86`), forcing an import alias.
- `FieldDefinition` and `InlineObjectPropertyDef` (`type-extractor/types/typescript.ts:91-111`) are field-for-field identical; `InlineObjectProperty` (`typescript.ts:123-128`) is a near-subset. This split alone is why **9+ near-duplicate collector functions** exist across `auto-type-generator.ts`, `inline-enum-collector.ts`, and `inline-union-collector.ts`.
- `DiagnosticCode` (`type-extractor/types/diagnostics.ts`, ~109 members) is pipeline-wide vocabulary (config, resolver, interface, auto-type codes) filed under one stage.
- Resolver results flatten inline-type info into ~10 parallel nullable fields (`returnTypeInlineObjectProperties`, `returnTypeInlineEnumMembers`, `returnTypeInlineUnionMembers`, … in `resolver-extractor/extract-resolvers.ts:17-61`) instead of carrying a nested `TSTypeReference`. This flattening is the direct cause of the "3 contexts × 3 features" collector duplication in auto-type-generator.

#### D. Copy-pasted algorithms that have diverged

- **`extractFieldsFromType` (`type-extractor/extractor/type-extractor.ts:453-590`) vs `extractArgsFromType` (`resolver-extractor/extractor/define-api-extractor.ts:364-416`)**: same pipeline (property symbols → optionality → TSDoc → metadata → `resolveFieldType`), but the args copy never detects directives, never skips `never`-kind types, and uses a bespoke TSDoc variant. See confirmed bug #1 below.
- **`determineTypeKind` vs `determineTypeKindFromType`** (`type-extractor.ts:763-785` vs `811-832`): the symbol-based path (used for re-exported types) never checks `isDefineInterfaceTypeAlias`, so a re-exported `GqlInterface` alias is silently classified as a plain object and loses interface semantics. No testdata case covers this.
- **The metadata-property walk** ("check own property → intersection members → union members") is independently reimplemented **5 times** (`default-value-detector.ts:48-79`, `directive-detector.ts:293-327`, `interface-detector.ts:35-72` (twice), `ignore-fields-detector.ts:26-53`, `metadata-detector.ts:155-171`), and the 4-line body of `typescript-utils.isNullOrUndefined` is copy-pasted 3 times instead of imported (`default-value-detector.ts:65-69`, `directive-detector.ts:311-314`, `directive-detector.ts:541-545`).
- **`convertToGraphQLType` inside `directive-definition-extractor.ts:231-402`** (172 lines) reimplements TS-type→GraphQL conversion instead of reusing `shared/type-converter.ts` / `PRIMITIVE_TYPE_MAP`.
- **`inline-object-converter.ts:15-55`** reimplements `convertTsTypeToGraphQLType` but omits the `stringLiteral`/`numericLiteral`/`union`/`never` branches — a strictly weaker copy (latent correctness gap for union-member fields of those kinds).
- **The "which generated-name map does this contextKey live in" decision tree** is implemented 4 times inside `auto-type-generator.ts` (`resolveFieldType` 660-717, `updateField` 749-878, `updateResolverField` 910-1027, `resolveMemberNames` region 1598-1658).
- **Two English pluralization dictionaries** with drifting word lists (`auto-type-generator/naming-convention.ts:58-210` singularizes; `shared/enum-prefix-detector.ts:35-113` pluralizes).
- **Two scalar-config formats** are both validated (`config-loader/validator.ts:290-467`): the legacy `graphqlName`/`type` shape is absent from the public `ScalarMappingConfig` type and the docs, yet most tests use it — and `defineConfig`'s own JSDoc example (`config/define-config.ts:12-23`) uses the legacy shape, meaning **the documented example does not type-check against its own parameter type**.
- `detectResolverFromMetadataType` and `detectAbstractResolverFromMetadataType` (`define-api-extractor.ts:205-241`, `116-163`) are ~90% identical and both call `checker.getTypeAtLocation(callExpr)` on the same node sequentially.

#### F. The CLI↔runtime contract is implicit and unenforced

The CLI does **not** detect gqlkit types by name — detection is shape-based via 10 space-prefixed marker properties (`" $gqlkitFieldMeta"`, `" $gqlkitScalar"`, …). This is a deliberate strength. But the contract is maintained as two independently-edited string sets: `runtime/src/index.ts` (embedded in type definitions) and `cli/src/shared/constants.ts:78-99` (`METADATA_PROPERTIES`), with **no test or shared module keeping them in sync** — and one hardcoded 11th copy already bypasses the constant (`type-extractor/mapper/scalar-base-type-mapper.ts:102`, verified). Renaming a marker on either side breaks generation silently.

Two syntax-fragile conventions sit on top: `define*` calls require explicit generic arguments (`extractTypeArgumentsFromCall`, `define-api-extractor.ts:475-483` reads `node.typeArguments` syntactically), and `implements` extraction (`shared/interface-detector.ts:77-176`) silently returns `[]` if the user wraps `GqlInterface`/`GqlObject` behind their own alias.

`packages/runtime/src/index.ts` is 875 lines mixing ~7 independent concerns, with `createGqlkitApis` being pure identity functions — the package's entire value is its types, yet **its only test file covers subscriptions** (`index.test.ts`, 141 lines); `GqlField`/`GqlObject`/`GqlInterface`/`GqlScalar`/`GqlDirective` and 4 of 6 `define*` functions have zero package-local tests.

#### G. `shared/` is ~43% mislabeled

10 of 23 modules have exactly one consuming stage (verified by grep): `file-scanner`, `program-factory`, `tsconfig-loader` (→ gen-orchestrator only); `branded-type-detector`, `interface-detector`, `ignore-fields-detector`, `ignore-fields-validator`, `inline-object-extractor`, `inline-object-utils` (→ type-extractor only); `interface-validator` (→ schema-generator only). `metadata-detector.ts` mixes a genuinely shared helper (`getActualMetadataType`) with a 134-line scalar classifier used by one stage.

### 1.3 Confirmed bugs found during the audit

All verified against the working tree; (1) and (2) reproduce in committed golden files.

1. **Argument directives are silently dropped for named args types.** `extractArgsFromType` never detects directives and `ArgumentDefinition`/`GraphQLInputValue` have no `directives` field. Committed evidence: `testdata/default-value-with-directives/.../schema.graphql` line 21 has `age: Int! = 18 @range(min: 0, max: 150)` on the input type, while line 28's `createUser(... age: Int! = 18 ...)` — flattened from the same `CreateUserInput` — has no directive and no diagnostic. Downstream is also unwired (`ast-builder.ts:265-290` never emits user directives on arguments; `result-integrator.ts:198-202`'s `UsageLocation` lacks `ARGUMENT_DEFINITION`).
2. **`CYCLE_DETECTED` diagnostics are lost for resolver args/return types.** `define-api-extractor.ts:614-637` creates `inputContext`/`outputContext` with their own `diagnostics: []`; grep confirms those arrays are never read back — only the local `diagnostics` is returned (line 779). The same cycle in a declared object type is correctly reported.
3. **Wrong diagnostic location for duplicate typenames.** `typename-validator.ts:313`: `const firstType = sortedTypes[1]!` — a variable named "first" bound to the second element.
4. **Directive-definition errors don't gate failure.** `extractDirectivesStep` pushes `severity: "error"` diagnostics into `ctx.diagnostics` (`orchestrator.ts:691-703`), but `validateExtractionStep`'s abort decision only inspects `typesResult`/`resolversResult` (`orchestrator.ts:708-725`) — a directive-definition error prints but exits 0. No testdata exercises `UNRESOLVABLE_ARG_TYPE`.
5. **File-write errors are swallowed.** `WriteResult.error` (`writer/file-writer.ts:14`) is discarded by `writeGeneratedFiles` (`orchestrator.ts:857-871`), so users only ever see "Failed to write output files".
6. **`hook-executor.ts:77-86`**: `execError.code` is typed as number but is the string `"ENOENT"` for spawn failures; `SingleHookResult.exitCode: number | null` can hold a string at runtime.
7. **Latent: pruning divergence.** If `enablePruning` is ever enabled, `sdlContent` is emitted from the pruned document but `typeDefsCode` is rebuilt unpruned (`generate-schema.ts:319-332` vs `code-emitter.ts:28-49`, which calls `buildDocumentNode` a second time).
8. **Latent: re-exported `GqlInterface` misclassification** (see §1.2-D).
9. **Type-level `@deprecated` on inline types is silently discarded**: `InlineObjectWithContext.deprecated` and `InlineEnumWithContext.externalEnumDeprecated` are collected but never read; `AutoGeneratedType` has no type-level `deprecated` field (`auto-type-generator.ts:114-135`).

### 1.5 Test infrastructure

Strengths: ~225 golden cases with a well-designed update mode (`golden.test.ts:28-41` auto-unlinks stale goldens under `-u`); error cases expressed as `diagnostics.json`; CI regenerates `examples/` and diffs; `full-featured`/`with-drizzle` run generated resolvers against real SQLite.

Debt:
- **Every golden case builds a fresh `ts.Program`** — `program-factory.ts:45` uses no shared `CompilerHost`/`DocumentRegistry`, so lib `.d.ts` files are re-parsed ~225 times per run.
- **Config-level features are outside golden reach**: output paths are hardcoded to defaults in the harness (`golden.test.ts:116-120`); zero cases set `sourceIgnoreGlobs`; hooks never run under `executeGeneration` (they live only in `commands/gen.ts`).
- `config-loader/validator.test.ts` is 1,174 lines of mostly table-drivable near-identical cases.
- `discriminator-field-validator.test.ts:10-126` and `discriminator-resolve-type-generator.test.ts:12-103` maintain near-verbatim duplicate mock builders, while `inline-collector.test.ts` shows the right pattern (reusing production factories from `ts-type-reference-factory.ts`).
- `packages/cli/src/testing/` contains only snapshot-update detection; temp-dir boilerplate is repeated across 4 test files.

### 1.6 Convention drift (CLAUDE.md rules vs reality)

The three documented conventions are followed at public boundaries and violated internally, consistently enough that the violations are systemic rather than incidental:

- **No default/optional params**: `convertTsTypeToGraphQLType(tsType, optional = false)` (`shared/type-converter.ts:55` — the most heavily used converter in the codebase), `scanDirectory(dir, options = {})` (`file-scanner.ts:119`), `collectScalars(..., options = {})` (`scalar-collector.ts:176-180`), `typenameAutoResolveTypeNames?:` (`abstract-resolver-validator.ts:19`), `onHookComplete?:` (`hook-executor.ts:16`).
- **Object args**: violated by ~11 helpers in `validator.ts`, most `ast-builder.ts`/`code-emitter.ts` builders, `extractDefineApiResolvers(program, files, options)`, `processExportDeclaration` (11 positional params), `extractInlineObjectProperties(type, checker, convertType)`.
- **null-not-undefined**: `ScalarTypeInfo.baseType: ... | undefined` (`types/typescript.ts:25`), `ScalarMetadataResult.error: ... | undefined` (`metadata-detector.ts:42`).
- **English-only**: Japanese JSDoc in `config/define-config.ts:4-5`.
- Spec-artifact comments (`Requirement 7.2` etc.) scattered in `auto-type-generator.ts` and `typename-validator.ts`.

## 2. Goals & Non-Goals

### Goals

1. **Restore true stage boundaries**: each pipeline stage exposes one entry function via `index.ts`; the orchestrator composes facades and contains no extraction/conversion logic of its own.
2. **Single-source the IR**: one home for `Diagnostic`, `SourceLocation`, `TSTypeReference`, `GraphQLFieldType`, field/property shapes, and marker-property constants; zero duplicate structural definitions.
3. **Eliminate diverged copies of algorithms** (field/arg extraction, metadata walks, type conversion, pluralization) so each behavior has exactly one implementation.
4. **Fix the confirmed bugs** (§1.3) with intentional, reviewed golden-file diffs.
5. **Make the CLI↔runtime contract explicit and tested.**
6. **Preserve extensibility**: adding a GraphQL feature (as the 35 specs in `.kiro/specs/` did) should touch one collector/one emitter, not 3–4 parallel copies.
7. **Keep every phase independently mergeable** with the full test suite green.

### Non-Goals

- No rewrite. The extraction engine (`resolveFieldTypeInternal`) encodes years of TypeScript-checker edge cases (alias normalization, `__type` symbols, `aliasTypeArguments` duality); it gets decomposed in place, never re-implemented from scratch.
- No user-facing API redesign: `createGqlkitApis`, `Gql*` utility types, naming conventions, and config schema stay as-is (except where a bug fix intentionally changes generated output). Decided exceptions: default-on schema pruning with a config opt-out (Phase 6, D1) and removal of the undocumented legacy scalar-config format (Phase 9, D2).
- No new runtime dependencies for generated code.
- No monorepo restructuring (package list stays cli/runtime/docs).
- Performance work is bounded: the golden-suite speedup and the double-extraction fix are in scope; broader optimization is not.

## 3. Target Architecture

### 3.1 Module layout (packages/cli/src)

```
core/                     # NEW — the IR and pipeline-wide vocabulary. Depends on nothing internal.
  diagnostics.ts          #   Diagnostic, Diagnostics, DiagnosticCode, SourceLocation, helpers
  ts-types.ts             #   TSTypeReference, PropertyDef (unified FieldDefinition/InlineObjectPropertyDef/InlineObjectProperty), factories
  graphql-types.ts        #   GraphQLFieldType, GraphQLTypeInfo, FieldInfo (single definition), TypeExtension
  metadata-contract.ts    #   METADATA_PROPERTIES, BUILT_IN_SCALARS, PRIMITIVE_TYPE_MAP, isTypenameFieldName, isEligibleField
shared/                   # True cross-cutting utilities only (~13 modules). Depends on core.
  (typescript-utils, tsdoc-parser, type-converter, directive-detector, directive-definition-extractor,
   default-value-detector, metadata-detector [getActualMetadataType only], enum-prefix-detector,
   pluralization [unified dictionary], diagnostics-utils, path-utils, string-utils, source-location)
type-extractor/           # Gains: extract-types.ts (real entry fn = today's extractTypesCore), branded-type-detector,
                          #   interface-detector, ignore-fields-*, inline-object-extractor/utils, scalar classifier
resolver-extractor/       # Gains: converter/ (today's convertDefineApiToFields + convertArgsToInputValues),
                          #   real entry fn returning ExtractResolversResult
auto-type-generator/      # Gains: inline-object-collector.ts (extracted from the god file), one resolveType facade
schema-generator/         # Gains: interface-validator, abstract-resolver-validator (moves here — it consumes BaseType);
                          #   integrate() split into mapper/root-types/extensions/directive-validation/enum-info modules
gen-orchestrator/         # Shrinks to: scan → program → stage facades → write → report. Gains: program-factory,
                          #   tsconfig-loader, file-scanner
commands/ config/ config-loader/ testing/   # unchanged homes; internal cleanups only
```

Dependency rule (enforceable, see §3.4): `core` ← `shared` ← stages ← `gen-orchestrator` ← `commands`. No stage imports another stage's internals; stage-to-stage data flows only through the types exported by `core` and each stage's `index.ts`.

### 3.2 Stage contracts

Each stage exports exactly one primary function plus its input/output types:

- `extractTypes(params) → ExtractTypesResult` — absorbs the two-pass scalar bootstrap (today in `orchestrator.ts:154-259`); later phases may replace pass A with a cheap scalar-declaration scan (Phase 10).
- `extractResolvers(params) → ExtractResolversResult` — absorbs `convertDefineApiToFields`; result carries **nested `TSTypeReference`** for args/returns instead of today's ~10 flattened `returnTypeInline*` fields (Phase 6).
- `generateAutoTypes(params) → AutoTypeGeneratorResult` — one facade; discriminator- and typename-based resolveType generation merge behind a single `collectResolveTypes` entry so `generate-schema.ts` stops hand-sequencing 9 internal calls.
- `generateSchema(params) → GenerateSchemaResult` — `buildDocumentNode` invoked once, both emitters consume the same document (fixes latent bug #7 by construction).

The shared type-resolution engine (`resolveFieldType`) remains in type-extractor but becomes an explicit, documented export of its `index.ts` — resolver-extractor consumes it as a declared dependency, not a deep import.

### 3.3 CLI↔runtime contract

- Marker-property names live in one place consumed by both sides. Simplest robust form: keep `METADATA_PROPERTIES` in `core/metadata-contract.ts` and add a **contract test** in the CLI package that reads `runtime/src/index.ts` source and asserts each marker string appears verbatim (the runtime package cannot import from the CLI, and the CLI deliberately has no runtime dependency — `knip.json:11` documents this).
- Fix the one hardcoded bypass (`scalar-base-type-mapper.ts:102`).
- Add a diagnostic for the silent `implements`-extraction failure: if a type has `$gqlkitInterfaceMeta`/`$gqlkitTypeMeta` semantically but syntactic extraction finds no tuple, warn instead of returning `[]`.
- Backfill `expectTypeOf` tests in `packages/runtime` for the four untested resolver kinds and the `Gql*` wrapper family before touching the file; then split `index.ts` by concern (`scalar.ts`, `field.ts`, `object.ts`, `interface.ts`, `directive.ts`, `resolver.ts`, `apis.ts`, barrel `index.ts`) — public API unchanged.

### 3.4 Enforcement

Conventions that aren't checked regress (this audit is the proof). Add to CI:

- **Dependency-direction check**: `dependency-cruiser` (new devDependency, Decision D7) over `packages/cli/src`, with declarative rules failing the build on stage-boundary violations (a stage importing another stage's internals) and on circular dependencies (Biome cannot express either).
- The runtime↔CLI **contract test** (§3.3).
- Keep `pnpm knip` green as modules move (it already exists; the moves will surface real dead exports).

## 4. Migration Strategy

Rules for every phase: independently mergeable PR(s); `pnpm check && pnpm typecheck && pnpm test && pnpm knip` green; golden files byte-identical **unless the phase explicitly says otherwise**; changesets only for phases marked user-visible.

### Phase 0 — Guardrails and dead-code removal *(no behavior change)*

1. Delete the dead first-gen resolver (`type-extractor.ts:131-417`), `excludePatterns` plumbing, dead barrel re-exports, the dead `argsTypeNode?` optionality. **Retain** the never-emitted resolver-validation codes (`UNSUPPORTED_RETURN_TYPE`, `UNSUPPORTED_ARG_TYPE`, `UNKNOWN_ARGUMENT_TYPE`) — reserved for Phase 9's resolver-side validation (Decision D6).
2. Fix `scalar-base-type-mapper.ts:102` to use `METADATA_PROPERTIES.SCALAR`; add the runtime↔CLI marker contract test.
3. Add the `dependency-cruiser` CI check (D7) in **report-only** mode (it will fail once §1.2-B is listed; baseline the known violations so new ones fail the build).
4. Golden-suite speedup: share a cached `CompilerHost`/`DocumentRegistry` across cases in `program-factory.ts` (behavior-neutral; verify by full-suite byte-identical goldens).
- **Acceptance**: goldens byte-identical; suite wall-clock measurably improved; contract test fails if a marker string is edited on either side.

### Phase 1 — Extract `core/` *(mechanical, no behavior change)*

1. Move `Diagnostic`/`Diagnostics`/`DiagnosticCode`/`SourceLocation` to `core/diagnostics.ts`; delete the duplicate `SourceLocation` definitions; re-export from old paths temporarily to keep the diff reviewable, then drop the re-exports in the same phase.
2. Move `TSTypeReference` + factories, `GraphQLFieldType`/`GraphQLTypeInfo` to `core/`; **unify `FieldInfo`/`AutoGeneratedField`/`BaseField` into one type** and delete `toBaseField`.
3. Move `METADATA_PROPERTIES`, `isTypenameFieldName`, `isEligibleField` into `core/metadata-contract.ts` — this breaks both the type-extractor↔auto-type-generator cycle and the shared→type-extractor cycle.
4. Rename one of the two `TypeExtension` types.
- **Acceptance**: goldens byte-identical; the two stage-level cycles this phase targets (type-extractor↔auto-type-generator, shared↔type-extractor) are gone from the baseline; boundary check is enforcing for `core` (dedicated rule, no baseline entries) and `shared` (zero remaining baseline entries). ### Phase 6 — Schema pruning as a default-on feature *(user-visible; BREAKING changeset)*

Decision D1: pruning is promoted from unreachable code to a first-class, **default-enabled** feature with a config opt-out. Rationale (maintainer): for large schemas, pruning unused types early is a practical size/performance win for downstream consumers, so the default should be on.

1. Precondition (delivered by Phase 3 per §3.2): `buildDocumentNode` is invoked once and both emitters consume the same document — this removes the typeDefs/SDL divergence (latent bug #7) *before* pruning can be enabled anywhere.
2. Add the config opt-out (final key name decided at implementation time, e.g. `output.pruning: false`, aligned with existing config naming); default **enabled**. Wire through `config/types.ts`, validator, loader, `GenerationConfig`, `generateSchema`; delete the hardcoded `enablePruning: null` and the unread `prunedTypes` or surface it in reporting.
3. Survey all ~226 testdata cases for output changes. Cases that intentionally assert unreferenced types in output get an explicit `pruning: false` in their `config.json` (requires threading pruning through the golden harness — coordinate with the harness generalization in Phase 9); every other golden diff is reviewed as the intended effect of the new default.
4. Add dedicated testdata cases: pruning-on (default) and pruning-off.
5. Fix and document precise semantics (which graphql-tools `pruneSchema` options apply: unused types, empty types, unused directives) in `packages/docs`.
6. Changeset with **BREAKING CHANGE**: generated output may drop types unreachable from root types; document the opt-out.
- **Acceptance**: golden diffs are exactly the pruning-induced removals plus the two new cases; `pruning: false` reproduces pre-phase output byte-identically.

Note (recorded during execution): the dry-run survey proved the inherited round-trip pruner (print→parse→`buildASTSchema`→`pruneSchema`) was unshippable — it crashed 13 cases (strict SDL validation gqlkit never enforced), ran on error paths, and its `printSchema` renormalization silently merged gqlkit's `extend type` blocks, restructuring ~88 schemas that had nothing to prune. `pruneDocumentNode` was therefore REWRITTEN as a pure reachable-set filter over the original DocumentNode (BFS from root operation types; implementers of reachable interfaces kept; ALL directive definitions kept with their arg types seeded; extensions kept iff their target is; no-root → no-op; skipped on error paths). A mandatory addition: the resolver map is filtered by the pruned set (`omitPrunedTypes`), otherwise dangling resolver entries break `makeExecutableSchema` at user runtime; custom scalars lost their old blanket exemption (pure reachability instead). Survey outcome: 19 cases pinned `pruning: false` (pruned type was the feature under test), 6 accepted incidental removals, 2 examples lost genuinely-dead demo types. `@graphql-tools/utils` became unused and was dropped from cli dependencies.

**Pre-existing bugs surfaced by the survey (NOT fixed here; unscheduled follow-ups):**
- **Subscription payload/args types referenced but never emitted**: `subscription-only`/`subscription-mixed`/`subscription-directives-tsdoc`/`import-extension-*` goldens contain fields typed `Event!`/`Message!` with no corresponding type definition — interfaces used as `defineSubscription` generics are referenced by name but never extracted. The committed schemas are rejected by `buildASTSchema`.
- **`$` leaks into emitted type names**: `union-dollar-typename-basic`/`union-typename-priority` emit `enum SearchQuery$typeNameInput` — invalid GraphQL grammar; the committed schema.graphql is unparseable by graphql-js.
- (Minor) argument defaults of custom-scalar/object type fail graphql-js `valueFromAST` coercion if the SDL is ever round-tripped through `buildASTSchema`.

## 5. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Golden tests are the only regression net for the two largest engines (`resolveFieldTypeInternal`, `extractTypesFromProgram` have no unit tests) | Keep refactors of those files strictly mechanical (extract-function only, in Phase 7); land the Phase 0 test speedup first so the full suite is cheap to run per commit; add characterization testdata cases before behavior-adjacent phases (4–6) |
| TypeScript-checker semantics are position-sensitive (alias vs expanded intersection, `__type` symbols, `aliasTypeArguments`) — moving detector code can silently change resolution paths | Phases 1–3 move files and rewire imports without editing function bodies; any signature change (object-args) is a separate commit from any move; goldens byte-compared per commit |
| User-visible output changes (Phases 4–6) surprise downstream users | Changesets with explicit before/after schema snippets; argument-directive fix is additive to generated schemas (fields gain directives, nothing is removed); pruning default-on ships with an opt-out that reproduces prior output byte-identically |
| Default-on pruning changes many goldens at once and could mask extraction regressions in cases that rely on unreferenced types appearing in output | Phase 6 surveys all ~226 cases before flipping the default; affected cases get explicit `pruning: false`; the pruning-off path stays golden-covered so extraction behavior remains observable |
| The 226-case golden suite might not cover a moved code path (e.g. re-exported interfaces, `UNRESOLVABLE_ARG_TYPE` today have zero cases) | Each phase that touches an uncovered path adds the covering testdata case *first* (listed explicitly in Phases 4, 5, 6, 9) |
| Long-running effort loses steam mid-way, leaving a half-migrated layout | Every phase leaves a consistent state (that's the phase-boundary criterion); the CI boundary check ratchets — once a rule is enforced it cannot silently regress; phases are ordered so the highest-value items (dead code, cycles, facades, bugs) land earliest |
| Import-path churn creates painful conflicts with in-flight feature branches | Phases 1–2 (the big path moves) should be scheduled in a quiet window and merged quickly; old paths get temporary re-exports within a phase only, never across phases |
| `knip`/`biome` false positives during moves | `pnpm knip` run per PR is already in the acceptance criteria; barrel churn is contained by finishing each move within one PR |
