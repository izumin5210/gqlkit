# Implementation Plan

## Task 1: Runtime 層の型定義と API 実装

- [x] 1.1 抽象型リゾルバの型定義と define 関数の実装
  - union/interface 型に対する型解決関数の型を定義し、メタデータを埋め込む仕組みを構築する
  - object 型に対する型判定関数の型を定義し、同様のメタデータ埋め込みを実装する
  - リゾルバ関数の引数として value、context、info を受け取り、適切な戻り値型を返す型を定義する
  - メタデータプロパティには既存パターンに従ったスペースプレフィックス付きの命名を使用する
  - 実行時には元のリゾルバ関数をそのまま返し、型情報のみを付与する実装とする
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 2.1, 2.2, 2.3, 2.4_

- [x] 1.2 GqlkitApis インターフェースへの統合
  - コンテキスト型を共有するファクトリ関数から新しい define 関数を返すよう拡張する
  - 抽象型リゾルバ定義関数がコンテキスト型パラメータを正しく引き継ぐことを確認する
  - 既存の defineQuery、defineMutation、defineField と一貫性のある API 設計を維持する
  - _Requirements: 3.1, 3.2, 3.3, 3.4_

## Task 2: CLI 抽出機能の拡張

- [x] 2.1 抽象型リゾルバ情報のデータ構造定義
  - リゾルバの種類、対象型名、エクスポート名、ソース位置を保持する構造を定義する
  - 既存の DefineApiExtractionResult を拡張し、抽象型リゾルバの配列を追加する
  - extractResolversCore の戻り値型にも抽象型リゾルバを含める拡張を行う
  - _Requirements: 4.5_

- [x] 2.2 メタデータマーカー検出と型パラメータ抽出の実装
  - エクスポートされた関数からメタデータプロパティを検出するロジックを追加する
  - 型パラメータから対象型名を抽出し、内部型シンボルの場合はフォールバック処理を行う
  - ソースファイルパスと行番号を記録してエラーレポートに活用できるようにする
  - エクスポート名から型を推測せず、メタデータの型パラメータのみを信頼する
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 10.1, 10.2_

- [x] 2.3 extractResolversCore への統合
  - 既存のリゾルバ抽出フローに抽象型リゾルバ抽出を組み込む
  - 抽出結果を ResolversResult に含めて後続の検証・生成フェーズに渡す
  - 診断情報を適切に収集して上位に伝播させる
  - _Requirements: 4.5_

## Task 3: CLI 検証機能の実装

- [x] 3.1 (P) 型参照の検証ロジック
  - 参照された型がスキーマに存在するか確認し、存在しない場合はエラーを出力する
  - resolveType で参照された型が union または interface であることを検証する
  - isTypeOf で参照された型が object 型であることを検証する
  - エラーメッセージには型名、ファイルパス、行番号を含める
  - 期待される型種類と実際の型種類の両方をエラーメッセージに記載する
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 8.1, 8.2_

- [x] 3.2 (P) 重複定義の検出ロジック
  - 同一の union/interface 型に対する複数の resolveType 定義を検出する
  - 同一の object 型に対する複数の isTypeOf 定義を検出する
  - すべての重複を単一の診断メッセージにまとめ、各定義の場所を列挙する
  - 最初の重複で停止せず、すべての重複を報告する
  - _Requirements: 7.1, 7.2, 7.3, 8.3_

- [x] 3.3 未定義警告の生成ロジック
  - union 型に resolveType が定義されておらず、構成型にも isTypeOf がない場合に警告を出す
  - interface 型に resolveType が定義されておらず、実装型にも isTypeOf がない場合に警告を出す
  - 警告メッセージに推奨される対応方法を含める
  - 警告はコード生成をブロックせず、ユーザーに表示するのみとする
  - _Requirements: 9.1, 9.2, 9.3, 9.4_

- [x] 3.4 検証パイプラインへの統合
  - 抽象型リゾルバ検証を既存の検証フローに組み込む
  - 型情報と抽象型リゾルバ情報を検証関数に渡す
  - 診断結果を統合してパイプライン全体の診断に追加する
  - 既存の診断フォーマットパターンに従ったエラー出力を行う
  - _Requirements: 8.4_

## Task 4: CLI 生成機能の拡張

- [x] 4.1 ResolverCollector による抽象型リゾルバ情報の収集
  - 抽出された抽象型リゾルバを生成用の構造に変換する
  - リゾルバの種類に応じて __resolveType または __isTypeOf のキーを決定する
  - ソースファイルとエクスポート名を保持してインポート文生成に活用する
  - _Requirements: 5.1, 5.2, 5.3_

- [x] 4.2 CodeEmitter による resolver map 出力の拡張
  - union 型の resolver オブジェクトに __resolveType を配置する
  - interface 型の resolver オブジェクトに __resolveType を配置する
  - object 型の resolver オブジェクトに __isTypeOf を配置し、既存フィールドリゾルバとマージする
  - 抽象型リゾルバのインポート文を生成する
  - 既存のエクスポートパターンを維持する
  - _Requirements: 5.1, 5.2, 5.3, 5.4_
